# Почему я выбрал такую схему

Я вынес код сервера в `inference`, вспомогательные команды в `tools`, а манифесты
в `deploy`. По пути файла теперь видно, относится он к обслуживанию запросов,
подготовке модели или развёртыванию.

## Раздельные контейнеры

Загрузчику достаточно стандартной библиотеки Python. Поэтому он собирается на
`python:slim` и не содержит vLLM или torch. Серверу не нужен доступ к HF token:
к моменту его запуска модель уже лежит в PVC. Оба контейнера работают от UID 10001.

При обновлении pod initContainer всё равно выполняется, но исправный snapshot
проверяется локально. Это позволяет использовать один путь запуска и при первой
установке, и при рестарте. Я не делаю сетевой запрос даже для проверки ревизии
в уже готовом кэше.

## Приватность журнала

Одного отключения access log недостаточно: текст запроса может оказаться в
исключении или выводе сторонней библиотеки. Поэтому я оставил отдельный процесс
для vLLM и направил его stdout и stderr в `/dev/null`.

ASGI middleware пишет короткое JSON-событие в отдельный pipe. Родительский процесс
пропускает только известные поля и проверяет их значения. Тела запросов и ответов,
query string, заголовки и тексты исключений в событие не входят. Для неизвестного
пути используется значение `other`, чтобы пользовательский URL тоже не попал в лог.

Цена этого решения — ограниченная диагностика: обычные сообщения vLLM не видны.
Для состояния запуска остаются события `server_starting`, `server_stopped`,
`startup_failed`, код завершения и Kubernetes probes. Я не предусмотрел переключатель,
который незаметно включает полный журнал на реальных запросах.

## Доступ и ограничения

Авторизацию API выполняет сам vLLM по ключу из Secret. Service имеет тип ClusterIP,
локальный доступ идёт через port-forward. Маршрут `/health` служит Kubernetes probes
и не требует Bearer token; запросы к `/v1` должны быть авторизованы.

У pod отключено автоматическое монтирование ServiceAccount token. Контейнеры
не могут повышать привилегии, запускаются с read-only root filesystem, без Linux
capabilities и с seccomp RuntimeDefault. Для временных данных выделены emptyDir.
Здесь rootless означает запуск процесса без root, как требует задание;
rootless-режим самого Docker daemon отдельно не настраивается.

## Воспроизводимость

Digest базового образа фиксирует его содержимое, а полный lock позволяет проверить
Python-окружение на этапе сборки. Эти два механизма используются вместе.
Для весов я закрепил HF commit SHA и сохраняю хеши локальных файлов в маркере.
Повреждённый snapshot не считается готовым, а временный каталог не выдаётся серверу
за завершённую загрузку.
